# Undo and Redo of Note Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ctrl+Z / Ctrl+Y (and ↶ ↷ in the top bar) undo and redo the last moves, renames, deletes
and creates of pages and sections, exactly or not at all.

**Architecture:** A session-only log (`src/undo.rs`) of what each user action did. Undo and redo
call the existing `mover` / `store` / `history` operations in "exact" mode: they get the wanted
names, and refuse *before changing anything* when a name is taken. The app records after each
successful user action and runs the steps with the existing follow-up code (index, tree, reopen).

**Tech Stack:** Rust 2024, egui/eframe, WebView2 (`assets/editor.js`). Tests: `#[cfg(test)]`
modules in the same file, temp folders under `std::env::temp_dir()` (see `mover::tests::temp`).

**Spec:** `docs/superpowers/specs/2026-11-17-undo-design.md`

## Global Constraints

- cargo is not on PATH in tool shells: bash `export PATH="$HOME/.cargo/bin:$PATH"`, PowerShell
  `$env:PATH = "$env:USERPROFILE\.cargo\bin;$env:PATH"`. Run commands in `H:\RAZVOJ\NoteCraft\app`.
- Never rewrite source files with PowerShell `Get-Content`/`Set-Content`; use the Edit tool.
- Commit messages: write to a file and `git commit -F <file>`; end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Branch `feat/undo` (exists).
- Session only, nothing written to settings or disk for the log. Depth **20**; a new action clears redo.
- Exact or refused: undo/redo never gives a "(2)" name and never overwrites; all checks happen
  before the first file changes. Names compare without case (`store::same_path`).
- Status texts: `Undone: <label>` / `Redone: <label>`; labels `move of "<name>"`,
  `rename of "<name>"`, `deletion of "<name>"`, `creation of "<name>"` (name = page title or
  section folder name as it was when the action ran). Refusals: `Cannot undo <label>: <reason>`.
- Hover texts: `Undo <label> (Ctrl+Z)`, `Redo <label> (Ctrl+Y)`; disabled: `Nothing to undo` /
  `Nothing to redo`.

## Review Focus

1. A page moved *with pictures that clashed* (renamed `x-2.png`) and then undone must link
   `x.png` again in the page **and** its versions, and `x-2.png` must be gone from the target when
   nothing else links it (Task 1 test `exact_back_restores_picture_names`).
2. Undo while the moved page is open in edit mode with unsaved text: the text is saved first and the
   page reopens in edit mode at its old place (Task 4, manual check M3).
3. Ctrl+Z typed in the search box, in a rename dialog, or while editing a page must not undo a move
   (Task 5, manual check M5).
4. Undo after "Purge history" removed the deleted item: refused with a message, record dropped,
   next Ctrl+Z goes on to the action before (Task 3 test `drop_failed_keeps_rest`, manual M6).
5. Redo of a move after another page with the same name appeared in the target: refused, no
   "(2)" (Task 1 test `exact_refuses_taken_stem`).

### Task 3: The undo log

**Files:**
- Create: `src/undo.rs` (declare `mod undo;` in `src/main.rs`)

**Interfaces:**
- Produces:
  ```rust
  pub const DEPTH: usize = 20;
  pub enum Step {
      MovePage { from: PathBuf, to: PathBuf, pictures: Vec<(String, String)> },
      MoveSection { from: PathBuf, to: PathBuf },
      RenamePage { from: PathBuf, to: PathBuf, old_title: String, new_title: String },
      RenameSection { from: PathBuf, to: PathBuf },
      Delete { path: PathBuf, entry: PathBuf, section: bool },
      Create { path: PathBuf, section: bool, entry: Option<PathBuf> },
  }
  pub struct Record { pub step: Step, pub label: String }
  #[derive(Default)] pub struct UndoLog { undo: Vec<Record>, redo: Vec<Record> }
  impl UndoLog {
      pub fn push(&mut self, r: Record);            // user action: cap DEPTH (drop oldest), clear redo
      pub fn take_undo(&mut self) -> Option<Record>;
      pub fn take_redo(&mut self) -> Option<Record>;
      pub fn undone(&mut self, r: Record);          // after a successful undo: onto redo
      pub fn redone(&mut self, r: Record);          // after a successful redo: onto undo, redo kept
      pub fn undo_label(&self) -> Option<&str>;
      pub fn redo_label(&self) -> Option<&str>;
  }
  pub fn invert(pictures: &[(String, String)]) -> Vec<(String, String)>; // swaps each pair
  ```
  A failed step is simply not given back (taken and dropped); the rest of the log stays.

- [ ] **Step 1: Write failing tests** in `undo::tests` (records with `Step::MoveSection` dummies):

### Task 4: Recording and running steps in the app

**Files:**
- Modify: `src/app.rs` (`NoteApp` field `undo: undo::UndoLog`, `do_dialog`, new `undo` / `redo`)
- Modify: `src/app/move_ui.rs` (`do_move`, `do_move_section`)
- Create: `src/app/undo_ui.rs` (`mod undo_ui;` beside the other `app` submodules) for `undo`, `redo`
  and the step runner, so `app.rs` does not grow further.

**Interfaces:**
- Consumes: Task 1-3 signatures.
- Produces (used by Task 5):
  ```rust
  impl NoteApp {
      pub(super) fn undo(&mut self);  // runs the last step backwards, sets the status line
      pub(super) fn redo(&mut self);
  }
  ```
- Refactor: `do_move(page, target_dir, exact: Option<&mover::Exact>) -> Result<Option<mover::Moved>, String>`
  and `do_move_section(folder, target, name: Option<&str>) -> Result<Option<mover::Moved>, String>`;
  the rename/delete/create follow-ups of `do_dialog` move into helpers taking explicit names
  (e.g. `rename_page_now(path, title, stem)`, `delete_page_now(path) -> PathBuf`, the same for
  sections) that `do_dialog` and the step runner both call. **Recording rule:** the user-facing
  paths (`exact`/`name`/`stem` is `None`) push a `Record`; the runner never does.
- Not recorded: a move with non-empty `left_behind` (append `\n\nThis move cannot be undone.` to the
  left-behind message).
- Runner, per direction, in this order, and refuse with `Cannot undo <label>: <reason>`
  (`Cannot redo …`) dropping the record:
  1. The item is where the record says (`to` for undo / `from` for redo; `entry` exists for a
     delete-undo or create-redo) — reason `it is not there any more`.
  2. Its place lies in an open top-level folder (`store::is_within(_, root)` for one of `self.roots`)
     — reason `its folder is not open in NoteCraft`.
  3. `page_free` / `folder_free` — their own text.
  4. The operation in exact mode (Tasks 1-2) — its error text is the reason (name taken).
  The open page is released with `release_open_page` before step 4 as the existing code does; if
  saving fails the record goes back on its list unchanged.
- Step table (undo / redo):
  - MovePage: `do_move(to, from.parent, Exact{stem: stem(from), pictures: invert(pictures)})` /
    `do_move(from, to.parent, Exact{stem: stem(to), pictures})`.
  - MoveSection: `do_move_section(to, from.parent, Some(name(from)))` / mirror.
  - RenamePage: `rename_page_now(to, old_title, Some(stem(from)))` / `(from, new_title, Some(stem(to)))`.
  - RenameSection: `relocate_folder(to, || store::rename_folder(to, name(from)))` / mirror
    (`rename_folder` already refuses a clash).
  - Delete: `restore_deleted(&deleted_item_at(entry)?, true)` + `after_restore_deleted` / delete
    again, storing the new entry in the record.
  - Create: delete it (entry stored) / exact restore from `entry`.
- After success: `reveal` = the item's new place (already done by the reused follow-ups), status
  `Undone: <label>` / `Redone: <label>`.
